# 오버워크드 (OVERWORKED) — 설계

*2026-08-26 · NAU 모델링팀 8인 온라인 협동 게임*

오버쿡드 방식의 협동 게임. 모델링팀의 실제 작업 파이프라인(모델링 → 리토폴 →
UV → 텍스처 → 리깅 → 렌더)을 조리 공정으로 치환해서, 마감 전에 에셋을 찍어낸다.

같은 팀을 위해 만든 [퇴근의 계단](https://mokh990322-source.github.io/toegeun-stairs/)의
후속작이며, 캐릭터·상점·지갑을 공유한다.

---

## 1. 무엇을 만드는가

- 2~8명이 각자 자기 자리 PC에서 브라우저로 접속하는 온라인 협동 게임
- 방 코드 4자리로 모인다
- 발주서가 날아오면 공정을 거쳐 에셋을 만들어 납품한다
- 목표 개수를 채우면 다음 스테이지. 총 6스테이지
- 순수 Canvas2D, 외부 라이브러리 0개, GitHub Pages 정적 호스팅

### 성공 기준

1. 팀원 8명이 각자 자리에서 접속해 한 판을 끝까지 굴릴 수 있다
2. 조작이 즉각 반응한다고 느껴진다 (내 캐릭터에 입력 지연이 체감되지 않는다)
3. 한 명이 튕기거나 나가도 나머지가 계속 플레이할 수 있다
4. 퇴근의 계단에서 번 코인으로 산 옷이 여기서도 그대로 보인다

## 2. 측정으로 확인한 제약

설계 전에 Firebase Realtime Database(싱가포르 리전)로 실측했다. 이 숫자가 아래
모든 결정의 근거다.

| 항목 | 결과 |
|---|---|
| 쓰기 왕복 | 76ms 중앙값 (min 75 / max 150, 편차 거의 없음) |
| 쓰기 → 다른 클라이언트 푸시 도달 | 76ms 중앙값 (min 75 / max 76) |
| SDK 없는 EventSource 스트리밍 | 작동함. `new EventSource(url + '/path.json')` 로 `put`/`patch` 이벤트 수신 |
| 푸시 도달률 | 12회 중 11회 |

**따라서 내 입력이 남의 화면에 뜨기까지 약 150ms**(입력 업로드 76 + 상태 푸시 76).

이 값이 배제하는 것:
- 픽셀 단위 정밀 점프·낙하 판정 — 억울한 죽음이 나온다
- 빠른 반사신경 대결 — 먼저 누른 사람이 진다

이 값이 허용하는 것:
- 걸어다니며 물건을 집고 옮기고 넣는 조작
- 순서와 분업을 말로 맞추는 플레이

가끔 한 프레임이 누락되므로 **상태는 항상 전체 스냅샷으로 보내고 보간으로 메운다**.
델타 전송은 한 번 누락되면 복구가 안 되므로 쓰지 않는다.

## 3. 네트워크 구조 — 호스트 권위 방식

### 3.1 검토한 대안

| 안 | 내용 | 판단 |
|---|---|---|
| **A. 호스트 권위** | 먼저 들어온 사람의 브라우저가 시뮬레이션 전체를 돌리고 결과만 뿌린다 | **채택** |
| B. WebRTC P2P | 사내망이면 5ms 이하. 하지만 8명이면 연결 28개, 방화벽에 막히면 대안 없음 | 미채택 |
| C. 각자 자기 캐릭터만 권위 | 두 명이 같은 물건을 동시에 집으면 서로 다른 화면을 본다 | 미채택 |

A를 고른 이유는 **물건 소유권 다툼이 원천적으로 생기지 않기 때문**이다. 오버쿡드류는
"이 접시를 누가 들었나"가 게임의 전부인데, 심판이 하나면 이 질문에 답이 하나뿐이다.

### 3.2 흐름

```
각 클라이언트                     호스트 브라우저
  방향/액션 입력  ──> in/<pid> ──>  모든 입력 수집
  (바뀔 때만 씀)                    60Hz 물리·판정 계산
                                          │
  화면에 그림    <── st ────────  10Hz 전체 스냅샷 PUT
  (보간 + 내 캐릭터 예측)
```

- **내 캐릭터**: 입력 즉시 로컬에서 움직인다(예측). 호스트 상태가 도착했을 때
  30px 이상 어긋나 있으면 0.2초에 걸쳐 부드럽게 끌어당긴다. 즉시 순간이동시키면
  고무줄처럼 보인다.
- **남의 캐릭터**: 스냅샷 두 개 사이를 보간한다. 100ms 지연 버퍼를 두어 한 프레임이
  누락돼도 끊기지 않는다.
- **물건·기계**: 호스트 상태를 그대로 따른다. 예측하지 않는다. 잘못 예측하면
  "집은 줄 알았는데 안 집혔다"가 되어 훨씬 나쁘다.

### 3.3 호스트 승계

호스트가 탭을 닫으면 판이 죽는다. 4분짜리 스테이지가 누가 alt-tab 했다고 날아가면 안 된다.

- 호스트는 매 스냅샷마다 `st/t`(틱 번호)를 올린다
- 3초간 `st/t`가 멈추면, 생존자 중 입장 순번이 가장 빠른 사람이 `meta/host`를 자기로 PUT
- 경합 방지: 승계를 시도한 뒤 1초 관망하고, `meta/host`가 자기가 아니면 물러난다
- 승계된 호스트는 마지막으로 받은 스냅샷에서 이어서 시뮬레이션한다

### 3.4 데이터 구조

```
rooms/<CODE>/
  meta   { host, phase: 'lobby'|'play'|'result', stage, born }
  who/<pid>   { name, char, gear:{hat,suit,back,trail,motion,stair}, join, seen }
  in/<pid>    { x: -1|0|1, y: -1|0|1, act, seq }
  st     { t, p:{<pid>:[x,y,dir,hold,work]}, o:[...], m:[...], ord:[...], score, left }
```

- 클라이언트는 `in/<자기 pid>`와 `who/<자기 pid>`만 쓴다
- 호스트만 `st`와 `meta`를 쓴다
- 이 규칙은 신뢰가 아니라 Firebase 보안 규칙으로 강제한다

**방 코드**: 4자리. `O/0`, `I/1` 처럼 헷갈리는 글자는 뺀 32자 집합에서 뽑는다.
URL 해시로 공유 가능 — `...#R=ABCD` 로 들어오면 코드가 자동 입력된다.

**방 청소**: 방이 쌓이면 저장소를 먹는다. 새 방을 만들 때 `born`이 6시간 넘은 방을
지운다(lazy GC). 별도 서버나 크론이 없으므로 이 방식뿐이다.

### 3.5 전송량 예산 (실측)

직렬화를 구현한 뒤 1스테이지(기계 5대) + 8명 만석으로 실측한 값이다.

| 항목 | 값 |
|---|---|
| 스냅샷 1개 | **271 bytes** |
| 호스트 업로드 (10Hz) | 2.6 KB/s |
| 한 판(4분) 전체 다운로드 | **5.0 MB** |
| Firebase 무료 티어 10GB/월로 가능한 판 수 | 약 2,000판 |

처음 계산값은 700 bytes / 13MB 였는데 절반 이하로 나왔다. 키를 한 글자로 줄이고
좌표를 정수로, 물건 이름을 색인으로 바꾼 효과다.

후반 스테이지는 기계가 5대에서 8대로 늘어 스냅샷이 조금 커지지만, 여유가 워낙
커서 10Hz를 낮출 이유가 없다. 하루 종일 돌려도 무료 티어 안이다.

### 3.6 보안 규칙 변경

지금 규칙은 `scores`만 열려 있고 나머지 경로는 전부 잠겨 있다(실측으로 확인:
`scores`에 필드를 하나 추가한 쓰기가 401로 거부됨). `rooms` 경로를 여는 규칙을
추가한다. **랭킹 규칙은 건드리지 않는다.**

```json
"rooms": {
  "$code": {
    ".read": true,
    ".write": "!data.exists() || newData.exists()",
    "meta": { ".validate": "newData.hasChildren(['host','phase'])" },
    "who":  { "$pid": { "name": { ".validate": "newData.isString() && newData.val().length <= 12" } } },
    "in":   { "$pid": { ".validate": "newData.hasChildren(['x','y'])" } }
  }
}
```

사내용이므로 인증까지는 두지 않는다. 대신 경로를 `rooms` 안으로 가두고 길이·타입을
검사해서, 실수나 장난으로 랭킹이나 다른 경로가 망가지지 않게 한다.

## 4. 게임플레이

### 4.1 조작

세 개뿐이다. 손이 아니라 머리가 바쁜 게임이 되게 한다.

| 키 | 동작 |
|---|---|
| WASD / 방향키 | 8방향 자유 이동 (격자 아님, 원형 충돌 반지름 14) |
| Space | 집기 / 놓기 |
| Shift | 작업 (연타) |

### 4.2 공정

```
레퍼런스 선반 → 모델링 데스크 → 리토폴로지 → UV 전개기 → 텍스처 베이커 → 리깅 데스크 → 렌더팜 → 납품대
```

물건은 상태 기계로 굴러간다.

| 단계 | 결과물 | 방식 |
|---|---|---|
| 레퍼런스 선반 | `ref` | 집으면 나온다 |
| 모델링 데스크 | `high` | 연타 |
| 리토폴로지 | `low` | 연타 |
| UV 전개기 | `uv` | 놓고 대기 (자동) |
| 텍스처 베이커 | `tex` | 놓고 대기. **방치하면 `burnt`** → 폐기통행 |
| 리깅 데스크 | `rig` | 연타 |
| 렌더팜 | `done` | 놓고 대기 (오래 걸림, 여러 개 동시 가능) |
| 납품대 | 납품 | 주문과 맞으면 점수 |
| 폐기통 | — | 망친 것을 버린다 |

주문서는 **어느 단계까지 요구하는지**로 정의된다. 1스테이지는 `low`까지, 6스테이지는
`done`까지. 그래서 공정 데이터 하나로 6개 스테이지를 다 만든다.

### 4.3 협동을 강제하는 장치

이게 없으면 8명이 각자 따로 노는 게임이 된다.

- **물건은 한 번에 하나만 든다** — 혼자 전 공정을 돌 수 없다
- **작업대는 한 사람이 점유** — 줄이 생기고, 누가 어디 설지 정해야 한다.
  예외는 렌더팜뿐이다. 렌더팜은 슬롯이 3개라 여러 개를 동시에 굽는다 —
  실제로도 그렇고, 5스테이지의 병목을 이걸로 푼다
- **대형 에셋은 두 명이 같이 들어야 한다** (4스테이지부터) — 피코파크의 그 감각
- **플레이어끼리 충돌한다** — 서로 몸으로 길을 막는다. 이게 웃음의 절반이다

> **충돌은 나중에 따로 넣었다.** 1단계를 다 만들고 나서야 전체 리뷰에서
> "8명이 같은 픽셀에 겹쳐 선다"는 게 드러났다. 위 세 줄을 스펙에 적어 놓고도
> 코드에는 몸으로 막는 장치가 하나도 없었다.
>
> 반지름 14px 원끼리 28px 안으로 들어오면 서로 절반씩 밀어낸다. 밀린 자리가
> 벽이면 그 사람은 안 움직인다 — 끼여서 겹치는 건 참을 수 있지만 벽을 뚫는 건 안 된다.
> 한 틱에 3번만 푼다(수렴할 때까지 돌리면 멈출 수 있다). 순서는 pid 정렬로 고정해
> 모든 클라이언트가 같은 답을 얻게 한다.
>
> **실측 — 기계 하나에 동시에 붙을 수 있는 인원:**
>
> | 기계 | 이론상 최대 | 8명이 몰렸을 때 실제 |
> |---|---|---|
> | ref1 / retopo1 (벽에 붙은 것) | 8명 | 4~5명 |
> | model1 / ship1 (벽에 붙은 것) | 7명 | 4명 |
> | bin1 (한가운데 열린 것) | 9명 | 7명 |
>
> 8명이 다 붙던 것이 4~5명으로 줄었으니 줄은 생긴다. 다만 **한 사람만 쓸 수 있는
> 수준은 아니다.** 기계가 두 칸짜리라 손 닿는 둘레가 넓기 때문이다. 이걸 더 조일지
> (닿는 거리를 줄이거나, 기계를 한 칸으로 만들거나, 점유 잠금을 넣거나)는
> 플레이테스트에서 판단한다 — 조작감을 모르는 채로 조이면 짜증나는 쪽으로 간다.
>
> 예측은 벽만 본다. 내 화면에서 남을 미는 예측을 하면 호스트와 싸운다 —
> 남의 위치는 150ms 과거라서 내 예측이 매번 틀린다.

### 4.4 주문

화면 위에 최대 3장. 각 주문은 요구 단계 + 제한시간을 가진다. 시간이 지나면
사라지고 벌점이 붙지만 **게임이 끝나지는 않는다**. 한 명이 실수했다고 전원이
죽으면 사내에서 하기엔 사이가 나빠진다.

## 5. 스테이지

목표 개수를 채우면 다음 맵. 6스테이지. 갈수록 공정이 늘어난다.

| # | 이름 | 공정 | 새로 나오는 것 |
|---|---|---|---|
| 1 | 인턴의 첫 발주 | 모델링 → 리토폴 | 기본 조작 |
| 2 | 언랩의 계절 | + UV | 대기형 기계 (놓고 기다린다) |
| 3 | 굽는 냄새 | + 텍스처 베이커 | **타는 것** — 방치하면 폐기 |
| 4 | 무거운 에셋 | + 리깅 | **두 명이 드는 물건** |
| 5 | 렌더 대기열 | + 렌더팜 | 긴 대기, 병렬 처리 |
| 6 | 마감 3일 전 | 전 공정 | 주문 폭주 |

각 스테이지 별 1~3개. 목표 개수에 따라.

**인원은 2~8명 유연.** 8명이 안 모여도 놀 수 있어야 한다. 인원 수에 따라 주문
빈도와 목표 개수를 조정한다.

## 6. 캐릭터와 상점 — 퇴근의 계단에서 그대로

### 6.1 지갑 공유

두 게임 모두 `https://mokh990322-source.github.io` 아래 경로에 올라간다.
localStorage는 오리진 단위이므로 **지갑과 보유 목록이 자동으로 이어진다.**
연동 코드가 필요 없다.

- `toegeun-stairs-coin` — 코인
- `toegeun-stairs-own` — 보유 목록
- `toegeun-stairs-equip` — 장착

키 이름은 퇴근의 계단 것을 그대로 쓴다. 이름이 게임 이름과 안 맞지만, 바꾸면
기존에 산 물건이 전부 사라진다. 그게 훨씬 나쁘다.

### 6.2 상점 6개 카테고리를 전부 살린다

| 카테고리 | 퇴근의 계단 | 오버워크드 |
|---|---|---|
| 계단 | 밟는 계단 색 | **작업대 상판 색** |
| 모자 | 머리 위 | 그대로 |
| 옷 | 캐릭터 색 | 그대로 |
| 등짐 | 등에 멘 것 | 그대로 |
| 발자국 | 점프할 때 | 뛰어다닐 때 |
| 모션 | 점프 모양 | 이동 모양 (회전·둥실·쿵쿵) |

### 6.3 코드 공유 방식

`js/shop.js`는 **복사본**이다. 두 저장소가 분리돼 있고, 크로스 저장소 include는
로컬 `file://` 테스트와 단일 파일 배포를 깨뜨린다.

- 두 파일의 카탈로그는 **항상 같아야 한다**. 양쪽 파일 머리에 쌍둥이임을 명시한다
- 한쪽에만 물건을 추가하면, 다른 쪽에서는 `Shop.get()`이 null을 돌려주고 그 물건이
  목록에서 사라진다. 저장된 데이터가 지워지지는 않으므로 복구는 된다
- 캐릭터 그리기(`player.js`)는 복사가 아니라 새로 쓴다. 탑다운이라 4방향 스프라이트가
  필요하고, 정면 픽셀 아트를 그대로 쓸 수 없다. 얼굴 사진 처리와 장비 파츠 좌표계는
  가져온다

### 6.4 코인 벌이

납품 1건당 코인을 준다. 두 게임의 벌이가 한 지갑에 합쳐지므로 **오버워크드 쪽을
짜게 잡는다**. 협동 게임이라 8명이 동시에 벌면 인플레가 빠르다.

## 7. 파일 구조

퇴근의 계단과 같은 방식. 클래식 `<script>` 태그만 쓴다 (ES 모듈은 `file://`에서 막힌다).

```
Overworked/
  index.html          화면·UI·스타일 (퇴근의 계단 Y2K 네온 픽셀 톤 유지)
  js/
    cloud-config.js   Firebase 주소
    net.js            EventSource 스트리밍, 쓰기, 재연결
    room.js           방 만들기/입장/대기실/호스트 승계
    shop.js           상점 (퇴근의 계단 쌍둥이 파일)
    sprite.js         캐릭터 그리기 (탑다운 4방향 + 얼굴 사진 + 장비)
    world.js          맵·충돌·좌표
    stations.js       공정 기계 정의와 상태 기계
    items.js          물건과 상태 전이
    orders.js         주문 생성·만료·채점
    sim.js            호스트가 돌리는 시뮬레이션 (여기만 권위)
    view.js           그리기 (보간·예측은 여기서)
    hud.js            DOM UI
    game.js           루프와 조립
  img/face/           팀원 얼굴 사진 (퇴근의 계단에서 복사)
  bundle.py           단일 파일 배포 빌드
```

**경계를 나눈 기준**: `sim.js`는 호스트에서만 돌고 네트워크를 모른다. `view.js`는
그리기만 하고 판정을 모른다. `net.js`는 게임을 모른다. 이 셋이 섞이면 "왜 내
화면에서만 다르게 보이지"를 추적할 수 없게 된다.

## 8. 만드는 순서

한 번에 다 만들면 8명이 붙었을 때 뭐가 터졌는지 알 수 없다. 3단계로 나눈다.

### 1단계 — 실제로 같이 되는지 확인
방 만들기/입장, 대기실, 8명 이동, 집기/놓기, 3공정 1스테이지, 호스트 승계.
**여기서 팀원들과 한 번 붙어본다.** 전송량도 이때 실측한다.

### 2단계 — 게임으로 만들기
스테이지 6개, 주문/채점/별점, 상점·캐릭터 이식, 코인 지급, 팀 랭킹.

### 3단계 — 회사 개그
방해요소: 갑작스러운 수정 요청(만든 걸 다시), 회의 소집(한 명이 15초 갇힘),
서버 다운(작업대 하나 20초 정지).

## 9. 안 넣는 것

- 모바일 대응 (사내 PC로 한다)
- 음성 채팅 (옆자리거나 이미 통화 중이다)
- 리플레이·관전
- 캐릭터 신규 제작 (퇴근의 계단 8명 그대로)
- 로그인·계정 (방 코드면 충분하다)

## 10. 위험 요소

| 위험 | 대응 |
|---|---|
| 전송량이 예산을 넘는다 | 1단계에서 실측. 넘으면 스냅샷 7Hz로 낮추고 좌표 정수화 |
| 호스트 PC가 느려서 전원이 렉을 먹는다 | 대기실에서 호스트를 수동으로 넘길 수 있게 한다 |
| 8명이 동시에 한 작업대로 몰린다 | 맵 설계로 분산. 1단계 플레이테스트에서 확인 |
| 두 게임의 shop.js가 갈라진다 | 파일 머리에 쌍둥이 명시. 카탈로그 변경은 양쪽 동시에 |
| 방 코드가 겹친다 | 방 생성 시 존재 여부를 확인하고 겹치면 다시 뽑는다 |
